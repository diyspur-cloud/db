**Projeto consultado:** `https://xjhehhfhhoomblcggjpk.supabase.co`.

Este documento contém pendências, implementações parciais e diferenças contratuais. Cada entidade existente deve ser reaproveitada. As correções propostas são código de desenvolvimento, não mudanças aplicadas ao projeto.

### Limites e força da evidência

- **Confirmado remoto:** resposta HTTP observada nesta análise, com chave publishable, sem cadastrar conta, gravar dados, disparar mensagens, enviar pagamento ou executar migrations. Consultas estruturais usam `limit=0`; isso não mede quantidade de registros nem valida isolamento entre usuários.
- **Confirmado no código:** leitura de arquivos no commit acima, considerando migrations posteriores às migrations-base. Há 93 arquivos de fonte/documentação lidos; bundles gerados não foram usados como uma segunda implementação.
- **Reprodução local:** PostgreSQL WASM/PGlite em scratch com roles/grants e funções extraídas da fonte; não substitui Supabase Auth ou teste hospedado autenticado.
- **Não verificável nesta sessão:** catálogo SQL administrativo, histórico remoto, secrets, configurações de backup, conteúdo não público e testes com JWT de usuário. O conector Supabase negou acesso SQL ao projeto Diyspur; a chave publishable não é credencial de administração. O OpenAPI na raiz `/rest/v1/` retornou 401 exigindo secret. Não classificar como ausente um objeto apenas por acesso negado.

A listagem anônima de buckets retornou `[]`: isso não prova que faltam buckets. As recusas de `select=*` em perfil, comentários, feed e quiz correspondem a grants restritos e não são, isoladamente, bugs. As diferenças de privacidade decorrentes desses grants são tratadas somente quando afetam o contrato do anexo.

Para arquivos SQL novos, executar `supabase migration new <nome>` e usar o timestamp realmente gerado. Neste texto, `<timestamp>_<nome>.sql` é um caminho proposto, não uma migration que já existe. ## 1. Buddy reads: leitura interrompida por recursão de RLS

**Referência no anexo:** §4.7 `buddy_reads`, `buddy_read_members`, `buddy_read_checkpoints`; §5.2 políticas Buddy Reads

**Arquivos envolvidos:**

- [supabase/migrations/20260101002300_rls_complement.sql](https://github.com/diyspur-cloud/db/blob/dc891b689b9937b8d286fc6b622c06927d8d4f64/supabase/migrations/20260101002300_rls_complement.sql) — existente.
- `supabase/migrations/<timestamp>_fix_buddy_read_policy_recursion.sql` — caminho proposto; não existe no snapshot.

**Estado:** falha confirmada na API remota.

| Rota consultada | HTTP | SQLSTATE | Resposta |
|---|---:|---|---|
| `/rest/v1/buddy_reads?select=*&limit=0` | 500 | 42P17 | `infinite recursion detected in policy for relation "buddy_reads"` |
| `/rest/v1/buddy_read_members?select=*&limit=0` | 500 | 42P17 | `infinite recursion detected in policy for relation "buddy_read_members"` |
| `/rest/v1/buddy_read_checkpoints?select=*&limit=0` | 500 | 42P17 | `infinite recursion detected in policy for relation "buddy_reads"` |

`buddy_reads_visible` consulta `buddy_read_members`; `buddy_members_read` consulta `buddy_reads`. A expansão de RLS forma um ciclo. `buddy_members_self_join` também consulta as duas relações. Os checkpoints herdam o problema ao consultar o pai.

**Passo a passo:**

1. Criar helper no schema `private` que verifique somente a condição booleana existente; fixar `search_path`, sem aceitar identidade enviada pelo cliente.
2. Substituir somente a leitura do pai pelo helper. Preservar a semântica do anexo nas políticas dos membros: a leitura de membros é pública se o buddy read for público, ou do owner se privado. Não ampliar convite/join além do texto original.
3. Não criar outra tabela de buddy read nem apagar memberships.
4. Reexecutar as três rotas e testar proprietário, membro, terceiro e anônimo com registros isolados.

**Código proposto para a migration:**

```sql
create or replace function private.can_view_buddy_read(p_id uuid)
returns boolean language sql stable security definer set search_path = '' as $$
  select exists (
    select 1 from public.buddy_reads br where br.id = p_id
      and (not br.is_private or br.owner_id = (select auth.uid())
        or exists (select 1 from public.buddy_read_members m
          where m.buddy_read_id = br.id and m.user_id = (select auth.uid())))
  );
$$;
revoke all on function private.can_view_buddy_read(uuid) from public;
grant usage on schema private to anon, authenticated;
grant execute on function private.can_view_buddy_read(uuid) to anon, authenticated;
drop policy if exists buddy_reads_visible on public.buddy_reads;
create policy buddy_reads_visible on public.buddy_reads for select
  to anon, authenticated using (private.can_view_buddy_read(id));
```

O helper é privilegiado estritamente para quebrar a consulta recursiva de autorização; retorna um booleano e fica fora da Data API. O owner da função precisa ser uma role confiável capaz de ler as duas tabelas sem reentrar em RLS. Manter `private` não exposto e sem `CREATE` para clientes.

**Aceite:** as três consultas deixam de retornar 42P17; buddy read privado continua invisível a terceiro; INSERT/DELETE seguem as condições do SDD. Ausência de erro com `limit=0` não encerra os testes de autorização.

## 2. Listas personalizadas: leitura interrompida por recursão de RLS

**Referência no anexo:** §4.8 listas e colaboradores; §5.2 Listas personalizadas

**Arquivos envolvidos:**

- [supabase/migrations/20260101002300_rls_complement.sql](https://github.com/diyspur-cloud/db/blob/dc891b689b9937b8d286fc6b622c06927d8d4f64/supabase/migrations/20260101002300_rls_complement.sql) — existente.
- [supabase/migrations/20261008225152_harden_core_authorization.sql](https://github.com/diyspur-cloud/db/blob/dc891b689b9937b8d286fc6b622c06927d8d4f64/supabase/migrations/20261008225152_harden_core_authorization.sql) — existente.
- `supabase/migrations/<timestamp>_fix_reading_list_policy_recursion.sql` — caminho proposto; não existe no snapshot.

**Estado:** falha confirmada na API remota.

| Rota consultada | HTTP | SQLSTATE | Relação indicada no erro |
|---|---:|---|---|
| `/rest/v1/reading_lists?select=*&limit=0` | 500 | 42P17 | `reading_lists` |
| `/rest/v1/reading_list_collaborators?select=*&limit=0` | 500 | 42P17 | `reading_list_collaborators` |
| `/rest/v1/reading_list_items?select=*&limit=0` | 500 | 42P17 | `reading_list_collaborators` |

`lists_read` consulta colaboradores; `list_collab_read` consulta listas. As políticas de escrita já alteradas continuam referenciando o pai. O helper de edição existente não eliminou o ciclo da leitura.

**Desenvolvimento:** criar helper booleano de visibilidade usando as condições exatas de `lists_read`, substituir a policy do pai e preservar as policies de escrita atuais. `unlisted` não deve virar público automaticamente: o anexo não faz isso na policy.

```sql
create or replace function private.can_view_reading_list(p_id uuid)
returns boolean language sql stable security definer set search_path = '' as $$
  select exists (
    select 1 from public.reading_lists l where l.id = p_id
      and (l.visibility = 'public'::public.reading_list_visibility
        or l.owner_id = (select auth.uid())
        or exists (select 1 from public.reading_list_collaborators c
          where c.list_id = l.id and c.user_id = (select auth.uid())))
  );
$$;
revoke all on function private.can_view_reading_list(uuid) from public;
grant execute on function private.can_view_reading_list(uuid) to anon, authenticated;
drop policy if exists lists_read on public.reading_lists;
create policy lists_read on public.reading_lists for select to anon, authenticated
  using (private.can_view_reading_list(id));
```

**Aceite:** consulta das três relações sem 42P17; colaborador lê lista compartilhada; terceiro não lê privada; `can_edit=false` não permite edição; troca de `list_id` não permite escrever em outra lista. Conferir também INSERT/UPDATE/DELETE dos colaboradores, pois esses caminhos precisam ler o pai.

## 3. Helper `is_admin()` incompatível com os grants atuais de perfis

**Referência no anexo:** §5.1 Helper: admin?; policies editoriais, Storage e newsletter

**Arquivos envolvidos:**

- [supabase/migrations/20260101001300_rls_policies.sql](https://github.com/diyspur-cloud/db/blob/dc891b689b9937b8d286fc6b622c06927d8d4f64/supabase/migrations/20260101001300_rls_policies.sql) — existente.
- [supabase/migrations/20261008225152_harden_core_authorization.sql](https://github.com/diyspur-cloud/db/blob/dc891b689b9937b8d286fc6b622c06927d8d4f64/supabase/migrations/20261008225152_harden_core_authorization.sql) — existente.
- [scripts/security-smoke/test.mjs](https://github.com/diyspur-cloud/db/blob/dc891b689b9937b8d286fc6b622c06927d8d4f64/scripts/security-smoke/test.mjs) — existente.
- `supabase/migrations/<timestamp>_restore_admin_predicate.sql` — caminho proposto; não existe no snapshot.

**Estado:** falha confirmada remoto e reproduzida localmente.

`GET /rest/v1/rpc/is_admin` retornou HTTP 401, SQLSTATE 42501, `permission denied for table profiles`. `is_admin` é SQL invoker na migration-base, e as posteriores apenas fixam seu search path. A coluna `profiles.role` deixou de ser selecionável por `anon`/`authenticated`. O helper não consegue verificar o papel do chamador.

A consulta de `newsletter_issues?select=id&limit=2` também retornou 42501 para `profiles`; a chamada de admin faz parte da policy desse recurso. Não liberar leitura de toda a tabela de perfis para corrigir o helper.

**Código proposto:**

```sql
create or replace function private.current_user_is_admin()
returns boolean language sql stable security definer set search_path = '' as $$
  select coalesce((select p.role = 'admin'::public.user_role
    from public.profiles p where p.id = (select auth.uid())), false);
$$;
revoke all on function private.current_user_is_admin() from public;
grant execute on function private.current_user_is_admin() to anon, authenticated, service_role;
create or replace function public.is_admin()
returns boolean language sql stable security invoker set search_path = '' as $$
  select private.current_user_is_admin();
$$;
```

O helper não aceita `p_user`, e usa exclusivamente `auth.uid()`. A role de usuário continua não editável. Esta forma segue o encapsulamento privado já usado no repositório para consultas autorizadas.

**Teste que falta no repositório:** o bootstrap de `scripts/security-smoke/test.mjs` declara `is_admin` como `SECURITY DEFINER`, diferente da migration-base. Os testes atuais passaram nesta execução, mas esse stub não reproduz o contrato real. Carregar a definição real no teste e exercer `SELECT public.is_admin()` diretamente como anon/leitor/admin, além de ao menos uma policy editorial e uma policy de Storage.

**Aceite:** anon e leitor recebem false, admin true, sem 42501; dados privados e `profiles.role` continuam sem SELECT direto pelo cliente. Não houve teste remoto como admin nesta sessão.

**Arquivos envolvidos:**

- [supabase/migrations/20260101001400_functions_and_triggers.sql](https://github.com/diyspur-cloud/db/blob/dc891b689b9937b8d286fc6b622c06927d8d4f64/supabase/migrations/20260101001400_functions_and_triggers.sql) — existente.
- [supabase/migrations/20260101002500_functions_complement.sql](https://github.com/diyspur-cloud/db/blob/dc891b689b9937b8d286fc6b622c06927d8d4f64/supabase/migrations/20260101002500_functions_complement.sql) — existente.
- [supabase/migrations/20261008225152_harden_core_authorization.sql](https://github.com/diyspur-cloud/db/blob/dc891b689b9937b8d286fc6b622c06927d8d4f64/supabase/migrations/20261008225152_harden_core_authorization.sql) — existente.
- `supabase/migrations/<timestamp>_restore_internal_counter_triggers.sql` — caminho proposto; não existe no snapshot.

**Estado:** incompatibilidade confirmada no código; reações, replies e streak reproduzidos em PostgreSQL WASM. Sem DML remoto.

| Operação local com role de cliente | Função da fonte | Resultado |
|---|---|---|
| Inserir reação | `bump_comment_likes` | 42501: permission denied for table comments |
| Inserir resposta | `bump_comment_replies` | 42501: permission denied for table comments |
| Inserir progresso | `touch_streak` | 42501: permission denied for table user_streaks |

As três funções são invoker. Os contadores de comentários não estão entre as colunas UPDATE concedidas ao cliente. `user_streaks` não tem policy de escrita de cliente. O problema de feed é inferência estática equivalente: `bump_feed_post_counters` também é invoker e tenta atualizar `likes_count`/`comments_count`, retirados dos grants de cliente.

**Desenvolvimento:** mover as operações internas de trigger para funções `private`, privilegiadas e não chamáveis por RPC; conservar as tabelas/regras de entrada existentes. Reapontar somente os triggers. Não conceder UPDATE direto de contador nem liberar escrita direta em `user_streaks`.

**Código de desenvolvimento:** reproduzir integralmente os quatro corpos das funções existentes em `private`, alterando somente o cabeçalho para `SECURITY DEFINER SET search_path=''` e qualificando todos os nomes de tabela. Os corpos completos são incluídos no apêndice de código ao final deste documento.

```sql
revoke all on function private.bump_comment_likes(),
  private.bump_comment_replies(), private.touch_streak(),
  private.bump_feed_post_counters() from public, anon, authenticated, service_role;
drop trigger if exists trg_comment_likes on public.reactions;
create trigger trg_comment_likes after insert or delete on public.reactions
  for each row execute function private.bump_comment_likes();
drop trigger if exists trg_comment_replies on public.comments;
create trigger trg_comment_replies after insert or delete on public.comments
  for each row execute function private.bump_comment_replies();
drop trigger if exists trg_streak_progress on public.user_progress;
create trigger trg_streak_progress after insert or update on public.user_progress
  for each row execute function private.touch_streak();
drop trigger if exists trg_streak_xp on public.xp_events;
create trigger trg_streak_xp after insert on public.xp_events
  for each row execute function private.touch_streak();
drop trigger if exists trg_feed_likes_counters on public.feed_post_likes;
create trigger trg_feed_likes_counters after insert or delete on public.feed_post_likes
  for each row execute function private.bump_feed_post_counters();
drop trigger if exists trg_feed_comments_counters on public.feed_post_comments;
create trigger trg_feed_comments_counters after insert or delete on public.feed_post_comments
  for each row execute function private.bump_feed_post_counters();
```

**Aceite:** A reage/responde ao conteúdo de B autorizado pelas policies, sem 42501; insert/delete mantém os contadores; UPDATE/UPSERT de progresso atualiza streak; usuário não altera contadores pelo REST. As policies e grants de cada tabela continuam sendo a porta de entrada. Esta correção não cria nova regra de pontos, likes ou streak além das existentes no SDD.

## 5. Onboarding não consegue gravar `level` e concluir `onboarding_done`

**Referência no anexo:** §4.2 `profiles`; §10 Onboarding

**Arquivos envolvidos:**

- [supabase/migrations/20261008225535_prevent_client_privilege_escalation.sql](https://github.com/diyspur-cloud/db/blob/dc891b689b9937b8d286fc6b622c06927d8d4f64/supabase/migrations/20261008225535_prevent_client_privilege_escalation.sql) — existente.
- [supabase/migrations/20261008225856_encapsulate_profile_consent_privilege.sql](https://github.com/diyspur-cloud/db/blob/dc891b689b9937b8d286fc6b622c06927d8d4f64/supabase/migrations/20261008225856_encapsulate_profile_consent_privilege.sql) — existente.
- `supabase/migrations/<timestamp>_restore_profile_onboarding_contract.sql` — caminho proposto; não existe no snapshot.
- `src/lib/supabase/onboarding.ts` — caminho proposto; não existe no snapshot.

**Texto exato do anexo:**

> **Onboarding** (`profiles.onboarding_done = false`): captura `username`, `display_name`, `level`, `lgpd_consent`.

**Diferença:** `level` no anexo é texto (`estudante`, `junior`, `pleno`, `senior`, `lideranca`). A migration de 2026-10-08 o redefine conceitualmente como atributo de progressão calculado pelo servidor e revoga UPDATE. Não há nova coluna separada de nível profissional, nem endpoint para gravar esse dado de onboarding. `onboarding_done` também não é gravável pelos grants finais. O trigger de cadastro não os preenche.

**Ajuste mínimo ao contrato anexado:** restaurar UPDATE somente dessas duas colunas pelo titular, mantendo `role` e `lgpd_consent_at` protegidos. Não criar outro nível ou outra tabela de perfil.

```sql
grant update (level, onboarding_done) on public.profiles to authenticated;
```

A policy `profiles_update_own` já limita `id=auth.uid()` antes e depois da alteração; confirmar o catálogo antes de executar. A lista de valores no anexo é um comentário exemplificativo, não um enum: não acrescentar um CHECK de domínio fechado sem novo requisito.

**Consumidor proposto:**

```ts
import { supabase } from './client';
export async function completeOnboarding(input: {
  username: string; display_name: string; level: string; lgpd_consent: boolean;
}) {
  const { data: { user }, error: authError } = await supabase.auth.getUser();
  if (authError || !user) throw authError ?? new Error('unauthenticated');
  const consent = await supabase.rpc('set_my_lgpd_consent', { p_consent: input.lgpd_consent });
  if (consent.error) throw consent.error;
  const result = await supabase.from('profiles').update({
    username: input.username, display_name: input.display_name,
    level: input.level, onboarding_done: true,
  }).eq('id', user.id);
  if (result.error) throw result.error;
}
```

Os dois comandos não são uma transação única: consentimento pode ser salvo e a atualização falhar, por exemplo por username duplicado. A tela precisa conservar os valores e permitir retry sem marcar sucesso. Não usar payload do usuário para atribuir `role`.

**Campo adicional existente no anexo:** `whatsapp` permanece lido por `get_my_profile_private`, mas não tem UPDATE concedido nem RPC de edição no snapshot. Caso o formulário de perfil do SDD use esse campo, conceder `UPDATE(whatsapp)` ao titular, sem expor SELECT público. A captura de WhatsApp não é requisito explícito do onboarding: não acrescentá-la à tela obrigatória.

**Aceite:** leitor conclui os quatro campos do anexo, reabre sessão e lê `onboarding_done=true`; leitor não altera outro perfil, `role` ou timestamp de consentimento.

## 6. Google e GitHub não habilitados no Supabase Auth

**Arquivos envolvidos:**

**Passo a passo:**

1. Configurar credenciais OAuth Google e GitHub nos próprios provedores. O callback Supabase é `https://xjhehhfhhoomblcggjpk.supabase.co/auth/v1/callback`.
2. Habilitar cada provider no painel Auth do projeto. Configuração local não modifica o painel remoto automaticamente.
3. Definir `site_url` e allowlist de redirects para a URL real da aplicação. O repositório só contém valores locais: não inventar domínio de produção.
4. Implementar chamadas abaixo no consumidor Next e callback que troca `code` por sessão.
5. Testar os dois provedores e verificar criação de profile/XP/streak pelo trigger, com usuários isolados.

```toml
enabled = true
client_id = "env(SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_ID)"
secret = "env(SUPABASE_AUTH_EXTERNAL_GOOGLE_SECRET)"
[auth.external.github]

client_id = "env(SUPABASE_AUTH_EXTERNAL_GITHUB_CLIENT_ID)"

```

```ts

import { supabase } from './client';
export async function signInOAuth(provider: 'google' | 'github') {

    provider, options: { redirectTo: `${location.origin}/auth/callback` },
  });

    email, options: { emailRedirectTo: `${location.origin}/auth/callback` },
  });
  if (result.error) throw result.error;

```

```ts
// src/app/auth/callback/route.ts — caminho proposto
import { NextRequest, NextResponse } from 'next/server';
import { getServerSupabase } from '@/lib/supabase/server';
export async function GET(request: NextRequest) {
  const code = request.nextUrl.searchParams.get('code');
  if (!code) return NextResponse.json({ error: 'missing_code' }, { status: 400 });
  const supabase = await getServerSupabase();
  const { error } = await supabase.auth.exchangeCodeForSession(code);
  if (error) return NextResponse.json({ error: 'invalid_code' }, { status: 400 });
  return NextResponse.redirect(new URL('/', request.url));
}
```

**Aceite:** Google e GitHub habilitados e login completo demonstrado; Magic Link e senha testados sem inferir sucesso a partir de `external.email=true`.

```sql
create or replace function private.club_progress_counts(p_club uuid)
returns table(finished_count bigint, reading_count bigint,
  not_started_count bigint, avg_percent numeric)
language sql stable security definer set search_path = '' as $$
  select count(*) filter(where up.status='read'),
    count(*) filter(where up.status='reading'),
    count(*) filter(where up.status='want_to_read'),
    coalesce(round(avg(up.percent)::numeric,2),0)
  from public.user_clubs uc
  join public.user_club_members m on m.club_id=uc.id
  left join public.user_progress up on up.user_id=m.user_id
    and up.chapter_id in (select c.id from public.chapters c
      join public.seasons s on s.id=c.season_id where s.book_id=uc.current_book_id)
  where uc.id=p_club and (not uc.is_private or uc.owner_id=(select auth.uid()));
$$;
revoke all on function private.club_progress_counts(uuid) from public;
grant execute on function private.club_progress_counts(uuid) to anon,authenticated;
```

**View completa proposta, preservando colunas atuais e acrescentando aliases:**

```sql
create or replace view public.v_club_progress_panel
with (security_invoker = true) as
select uc.id as club_id, uc.name as club_name,
  uc.current_book_id, b.title as current_book_title,
  uc.current_season_id, cs.title as current_season_title,
  uc.current_started_at, uc.current_ends_at,
  old_panel.distinct_readers,
  ag.finished_count as chapters_read,
  ag.reading_count as chapters_in_progress,
  ag.avg_percent,
  ag.finished_count, ag.reading_count, ag.not_started_count
from public.user_clubs uc
join public.user_club_members member_scope on member_scope.club_id=uc.id
left join public.books b on b.id=uc.current_book_id
left join public.seasons cs on cs.id=uc.current_season_id
cross join lateral private.club_progress_counts(uc.id) ag
cross join lateral (
  select count(distinct up.user_id) filter(where rs.id is not null) as distinct_readers
  from public.user_club_members m
  left join public.user_progress up on up.user_id=m.user_id
  left join public.chapters c on c.id=up.chapter_id
  left join public.seasons rs on rs.id=c.season_id and rs.book_id=uc.current_book_id
    and (uc.current_season_id is null or rs.id=uc.current_season_id)
  where m.club_id=uc.id
) old_panel
where uc.current_book_id is not null
group by uc.id,uc.name,uc.current_book_id,b.title,uc.current_season_id,cs.title,
  uc.current_started_at,uc.current_ends_at,old_panel.distinct_readers,
  ag.finished_count,ag.reading_count,ag.not_started_count,ag.avg_percent;
```

## 15. Filtro da newsletter criado pelo seed é rejeitado pelo handler

**Referência no anexo:** §11.2 newsletter; §9.8

**Arquivos envolvidos:**

- [supabase/seed_complement.sql](https://github.com/diyspur-cloud/db/blob/dc891b689b9937b8d286fc6b622c06927d8d4f64/supabase/seed_complement.sql) — existente.

**Estado:** incompatibilidade confirmada no código. O seed do anexo e do repo cria `audience_filter={"tags":["welcome"]}`. O handler atual aceita somente `frequency`, `tags_any`, `tags_all`; essa edição é rejeitada com `unsupported_audience_filter`, HTTP 422.

**Passo a passo:** admitir `tags` como alias de compatibilidade, ou retirar o filtro se a intenção for reproduzir exatamente o handler do anexo (que envia a todos os confirmados). Não trocar silenciosamente por uma semântica nova: o anexo define o campo, mas seu handler não aplica filtro.

**Patch de compatibilidade proposto:**

```ts
const allowedKeys = new Set(['frequency', 'tags_any', 'tags_all', 'tags']);
if (Object.keys(filterObject).some(key => !allowedKeys.has(key))) {
  return json({ error: 'unsupported_audience_filter' }, 422);
}
for (const key of ['tags_any', 'tags_all', 'tags'] as const) {
  const value = filterObject[key];
  if (value !== undefined && (!Array.isArray(value) || value.length > 50 ||
    !value.every(tag => typeof tag === 'string' && tag.length <= 80))) {
    return json({ error: 'invalid_audience_filter' }, 422);
  }
}
// No filtro de destinatário, caso a decisão seja alias para qualquer tag:
const any = (filterObject.tags_any as string[] | undefined)
  ?? (filterObject.tags as string[] | undefined) ?? [];
```

O patch só deve usar `tags` como alias após explicitar que a regra é “qualquer tag”. Se a exigência literal for o código do anexo, `audience_filter` não filtra: manter disparo para todos os confirmados. Essas duas opções não são equivalentes e o SDD não escolhe uma terceira.

**Aceite:** a edição gerada pelo próprio seed não recebe 422; conjunto de destinatários esperado explicitado; reexecução sem duplicar entregas já enviadas. O envio real não foi executado nesta análise.

14. **Seeds operacionais:** vídeo placeholder, nenhum conjunto completo de reuniões no seed-base, textos/layouts de jogos e prompts não exaustivos. O seed é demonstrativo. Não inventar dados reais para simular conclusão de calendário/vídeo.
15. **Arquivos compartilhados anunciados:** árvore do anexo prevê `_shared/supabaseAdmin.ts` e `_shared/types.ts`, mas não fornece conteúdo. A fonte utiliza `_shared/auth.ts` para clientes/auth e tipos locais/gerados. Não criar módulos vazios duplicados apenas para igualar nomes; registrar diferença de organização, sem classificá-la como funcionalidade ausente.
16. **Nome na arquitetura:** diagrama menciona `next-book-vote`, mas §9.3/9.12 exigem `vote-next-book`. O handler real usa o nome da seção executável; não publicar uma segunda função alias sem requisito.

**Passo a passo documental:** para cada conflito, manter o texto original da referência, anexar a divergência concreta e explicitar se a mudança é correção técnica, compatibilidade de API ou regra de negócio ainda indefinida. create or replace function private.bump_comment_likes()
```sql
returns trigger language plpgsql security definer set search_path = '' as $$
begin
  if tg_op = 'INSERT' then
    update public.comments set likes_count = likes_count + 1 where id = new.comment_id;
  elsif tg_op = 'DELETE' then
    update public.comments set likes_count = likes_count - 1 where id = old.comment_id;
  end if;
  return null;
end $$;
```

```sql
create or replace function private.touch_streak()
returns trigger language plpgsql security definer set search_path = '' as $$
declare
  v_user uuid;
  v_last date;
  v_today date := current_date;
  v_curr int;
  v_long int;
begin
  -- quem gerou atividade?
  if tg_table_name = 'user_progress' then v_user := new.user_id;
  elsif tg_table_name = 'xp_events'   then v_user := new.user_id;
  else return null; end if;

  select last_activity_at, current_streak, longest_streak
    into v_last, v_curr, v_long
  from public.user_streaks where user_id = v_user for update;

  if v_last = v_today then return null; end if;

  if v_last = v_today - 1 then
    v_curr := coalesce(v_curr,0) + 1;
  else
    v_curr := 1;
  end if;
  v_long := greatest(coalesce(v_long,0), v_curr);

  update public.user_streaks
     set current_streak = v_curr,
         longest_streak = v_long,
         last_activity_at = v_today,
         updated_at = now()
   where user_id = v_user;

  return null;
end $$;
```

```sql
create or replace function private.bump_feed_post_counters()

      update public.feed_posts set comments_count = greatest(comments_count - 1, 0) where id = old.post_id;
    end if;
  end if;
  return null;
end $$;
```
